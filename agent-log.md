### Architecture proposal — not an implementation claim

- **Capture integration:** an OpenCode integration establishes a pre-execution barrier at a user-turn boundary and associates the turn with immutable capture identifiers.
- **Transport recorder:** a local forwarding proxy records the serialized outgoing model request and associates each call with its session, user turn, and attempt. It must exclude authorization secrets from persisted records.
- **Workspace store:** content-addressed blobs plus persistent manifests preserve file contents and metadata. The proposed metadata includes relative path, type, permissions, and symlink target. Required ignored/untracked files need an explicit capture policy; caches may be excluded only when reproducible reconstruction is defined.
- **Context store:** preserve session records, tool outputs, attachments or referenced artifacts, compaction state, resolved instructions, tool schemas, and model parameters as needed to reproduce the supplied input. Session export alone is not assumed to contain the final provider request.
- **Runtime package:** share pinned container images across tasks. Store task-specific workspace/context references separately. Use a Harbor-shaped task directory with a custom capture extension; exact OpenCode restoration is the responsibility of our adapter, not presumed native Harbor functionality.
- **Replay worker:** start an isolated writable runtime, restore the selected pre-request state, submit the request exactly once, and exclude the original failed assistant/tool suffix from active context. Retain that suffix only as attempt evidence.
- **Checkpoint command:** `!checkpoint` selects the last eligible user turn by default, with an explicit earlier-turn selector. The checkpoint command itself must not become the selected task. It packages, restores, validates, runs a bounded cheap-model attempt, and prints a fixed status.

These bullets are design proposals, not externally verified behavior. [Citation: synthesized architecture from the independent-design, capture-feasibility, and build-sequence subagent reports in this conversation; they require the technical spike below.]

### Technical spike specification — proposed

1. Pin OpenCode and compatible plugin/SDK versions. Record exact versions and source revision.
2. Create a two-turn coding fixture containing a tracked edit, an untracked file, an ignored-but-required file, a deletion, and a symlink.
3. Artificially delay capture. Verify that no first model request or tool action starts before capture commits.
4. Restore the selected turn into a clean container and isolated OpenCode session store. Preserve the same working-directory layout where required.
5. Intercept the regenerated request before forwarding. Compare semantic request fields, context, tool schemas, parameters, and workspace hashes/metadata. Identify volatile transport fields explicitly rather than silently discarding differences.
6. Restore twice and compare both initial states. Ensure the chosen user request occurs once and the original failed suffix is absent.
7. Run the cheap-model smoke attempt as a separate override. Do not confuse model-override differences with failure of original-model input equality.
8. Run deterministic tool probes and positive/negative task-verifier fixtures. Persist structured results and emit fixed PASS/FAIL/INCONCLUSIVE output.

This is a proposed validation sequence; no execution result is claimed. [Citation: capture-feasibility and build-sequence subagent reports, followed by user instruction “for 1 you do that. for 2 also do that”.]

### Open questions and dependencies

- Can the pinned OpenCode integration block execution at the required boundary and reliably identify session/turn IDs?
- Can import/continuation regenerate the original effective model input, including compacted history and referenced artifacts?
- How are background/title/compaction calls distinguished from task calls at the proxy?
- What workspace exclusions and dependency reconstruction rules are acceptable?
- How are external services, running processes, writable state outside the workspace, and queued user turns detected and reported as unsupported?
- Which runtime image, cheap model, and smoke-test limits will be selected? Earlier numerical limits were proposals and are not recorded here as approved requirements.
- If plugin/proxy replay fails, is a small pinned OpenCode patch sufficient? This is the proposed fallback, not yet a required implementation.

These are unresolved questions, not factual claims. **Next action:** draft the concise MVP design for joint review, then perform the technical spike before expanding implementation.

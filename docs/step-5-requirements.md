# Step 5 — Checkpoint command and live smoke test requirements

## Goal and boundary

One !checkpoint invocation selects an attempt, exports a portable candidate, restores/checks it, and makes a short real-model/tool attempt. Reuse Step 4 packaging and Step 3 restoration. Do not implement a second exporter or restore path.

S5-R1–R5 define this step's completion gate. New requirements need user approval. Runtime readiness is separate from RL reward correctness. No VM deployment or batch scheduling belongs here.

## Required implementation locations

Use src/checkpoint/ for orchestration, a project-controlled bin/checkpoint executable for OpenCode's shell PATH, docs/checkpoint.md for installation/selection/status rules, tests/checkpoint/ for deterministic failure tests, and tests/live/checkpoint.live.test.ts for the opt-in real-model workflow. Save reports and transcripts under ignored work/checkpoint/<run-id>/.

These are implementation targets, not claims that the files/commands exist. Live tests must stay outside default verification. Controlled failures use deterministic injections; successful live integration uses a real provider/model and real OpenCode tools.

## Requirements and evidence

| ID | Requirement | Required evidence |
|---|---|---|
| S5-R1 | !checkpoint selects the most recent eligible request in the active session by default. An explicit checkpoint/turn selector can choose earlier state. Never select another session globally or capture the command itself as the task. | Real OpenCode invocation after two turns selects turn two; explicit selection chooses turn one; repeated prompt text uses identity; ambiguous/missing session fails. |
| S5-R2 | Save the package first, then run existing package/restore checks. Stop before inference if those checks fail. | S5-R3 | Make a bounded real OpenRouter model attempt in the restored container. Require a valid response and real tool execution. Record model override separately from original-input equality. Provide credentials only at runtime. | Opt-in live fixture executes a file tool and leaves deterministic evidence. Verify provider/model restriction, request/token/time limits, key-budget preflight, and no persisted credential. Missing key, exhausted budget, provider error, and timeout do not pass. |
| S5-R4 | The script, not the model, prints a fixed result and task ID. PASS means restore and agent/tool readiness; FAIL means a failed check; INCONCLUSIVE means a bounded provider/model attempt could not establish readiness. Keep detailed transcripts separate from the short confirmation. | Snapshot exact success/failure/inconclusive message formats. Verify nonzero exit for non-PASS, report paths, preservation of packages, and separate structured check/model results. No task-solution claims are generated by the model. |
| S5-R5 | Clean up run-owned containers/processes, retain task/evidence data, and support a subsequent explicit retry without changing the saved candidate. Keep live tests opt-in after major integration changes. | Run success, missing-key, timeout, and tool-failure cases; check cleanup and retained package hashes; run a fresh retry from the same candidate. |

## Completion gate

All S5-R1–R5 pass, including one real OpenCode !checkpoint invocation and one successful real-provider/tool case. Existing deterministic and real-container suites pass. Append cited results, revision, costs/budget evidence, and package/report paths to agent-log.md.

Output: working project-local !checkpoint workflow and fixed confirmation. Next: Step 6 VM setup, with provider-specific requirements reviewed before implementation.
